# AONの命名・採用と、実現の哲学での位置づけ

## 初期の方法論上の論点（開発者の見解）

・YAGNI はアンチパターンたり得る
YAGNIはアンチパターンになりえる。
前提条件として、AIを用いて大規模かつ並列的に作業を行う効率化を図ることで旧時代の作業効率的価値観は通用しない。　また、同時にAIを用いた作業ではより堅牢かつ柔軟な高級的実装が適切になる。　またAIはYAGNIを理由に設計コストを後回しにしてしまう。この場合、後回しにするというコンテキストが喪失することが多く、その場合根本的な設計破綻を内包することになる。
YAGNIが適用できるものは、ドメイン知識として不要と判断されるものに限られる。
ドメイン知識として現在の開発目標から著しく外れた要求であれば適用可能。そうでない場合は適用することを控えても構わない。
だが、上記のYAGNI適用の可否基準は拡張性を判断する際のみ適用可能である。
内部実装の堅牢可や基盤実装の設計時にはYAGNIの適用はより一層適用は渋るべきだ。

なるほど。　ただもう少し厳しめでもいいかな。やっぱり、YAGNIをコスト回避だけを主目的に使わないという制約を強く掲げたいんだよね。　　作ってしまったら整合性担保が難しくなるとか、作る理由自体がそもそもないとかならいいんだけど、　　作ったらよりよくなるし作る理由も凄いあるけどコストが高いからいらない。　は避けたい。

## 経路探索の契約と内部実装についての検討

例えば、適切に　インターフェイス　面を定義できるなら、内部実装はどうでもいいというのがカプセル化の境界面理論だよね。　具体例でいえば、　経路探索アルゴリズムの契約面では、絶対にYAGNIを適用してはいけないけど、実際の内部の実装は別にYAGNIでいいんだよね。

両者は両立し得るが、将来の必要がまだ定まらない場面でも内部を先に堅牢にすることに、どこまで積極的な価値を認めるかは確定できない。

## YAGNIに加えて必要とした指針

前の議論で境界の話があったけど、これはもっと抽象で

何かを開発したり作業をしていくうえでYAGNIではない別の指針が欲しいんだよね。

それが

YAGNI が禁じるのは投機的な機構（使われない interface・余分な継ぎ目・早すぎる共有モジュール抽出）。

hardeningを待てるのは「まだ何を固めるべきか分からない」からであり、「固めるのが大変だから」だけではない。

**仮の抽出候補：** YAGNIにより将来を予測した公開機能や内部機構の追加を抑える一方、現在選んだ責務を成立させるために必要な契約・保証を、作成コストが高いという理由だけで省略しない。

## 必要性と実施負担を分ける案

「必要であるかどうか」と「実現するのが大変かどうか」を混同してはならない。

YAGNIは主として「不要なものを作らない」という方向ですが、あなたが求めている原則には、もう一方の強い主張があります。

必要なものは、実現が困難だからという理由で不要にしてはならない。

## 最初の命名候補

| 名称 | 特徴 |
| --- | --- |
| 必要性本位原則 | 必要かどうかを判断の中心に据える。最も抽象的で汎用的 |
| 必要性優先原則 | コストや容易さより必要性を優先する。規範として強い |
| 必要性・実施負担分離原則 | 必要かどうかと、どう実現するかを区別する。意味が明確 |
| 必要完遂原則 | 必要だと認めたものを省略せず成立させる。責任を強調 |
| 非投機・必要充足原則 | 根拠のない先回りを抑え、必要なことを満たすという両面を表す |

私の第一候補は「必要性本位原則」

例えば、次のように定義できます。

必要性本位原則 何を行うべきかは、その目的と引き受けた責務に照らした必要性によって判断する。 根拠のない将来予測によって不要なものを追加してはならない。 一方、必要であると判断したものを、実現の困難さや費用の大きさだけを理由に不要とみなしてはならない。 必要性の判断と、実現方法・実施順序・負担への対処は区別する。

ここで重要なのは、 費用を無視しろという原則ではない ことです。

必要な仕事が大変なら、実施方法を工夫する。段階的に進めることもできる。場合によっては目的や要求そのものを再検討することもある。

ただし、「大変だから本当は必要ないことにしよう」という判断を許さない。

これならプログラミングだけでなく、ドキュメント管理、設計、調査、品質保証、組織運営などにも適用できます。

ただ、私はもう一つの候補、**「必要性・実施負担分離原則」**も捨てがたいと思っています。

こちらは、なぜその原則が必要なのかが名称から直接伝わるんですよね。

そして少し気になっていることがあります。

あなたがこれまで強調してきた「さぼるな」は、単に必要な作業を省略するなという意味ではなく、 必要性そのものを、都合のよい理由で歪めるな という思想にも見えます。

だとすると、

必要性本位原則 ：何を行うべきかを決める根本思想

必要性・実施負担の分離 ：その思想から導かれる具体的な判断規律

という関係にするのも自然です。

私はこの二段構えを推したいですね。

## NiNという案と、その限界

そうだね、YAGNIみたいに表したいんだよね
必要なものは必要だという原則
Need is Need でNiN　とかはどう？
でもこれだと　今はその実装が絶対に必要ないという物は必要ないというニュアンスが抜けてしまうか

「必要なものは必要だ」だけでは、「不要なものは作らない」が論理的には導かれません。

## All、Only、Necessary

All ：必要なものは、困難でも高コストでも省略しない。

Only ：必要でないものは、将来使うかもしれないというだけで追加しない。

Necessary ：何が必要かは、目的と引き受けた責務から判断する。

YAGNIが主に「作りすぎるな」という方向の原則なら、AONは 過剰も不足も許さない 原則です。

私は、思想としての意味の完全性ではAONを推します。

ただし、NiNにも魅力があります。特に「必要なことを大変だから不要扱いするな」という強い意志が、よく出ています。

この原則では、 必要性と実施負担を別の判断として扱う ことを明文化したいですね。

例えば、目的に対して本当に必要な設計があるとして、その実装に100時間かかる。

100時間かかるという事実は、その設計が不要である証拠にはならない。

一方、今の目的や責務に対して必要性のない機能なら、たとえ5分で実装できても、追加を正当化しない。

ただし、実現が難しい場合に目的やスコープ自体を再検討することはできます。 必要性を偽ることと、目的を正当に変更することは違う からです。

AON — All and Only Necessary 必要なものはすべて。必要なものだけ。 目的と責務に照らして必要なものを、実現の困難さを理由に省略してはならない。 同時に、必要でないものを、可能性や容易さだけを理由に追加してはならない。 必要性の判断と、実現方法・費用・実施順序の判断を混同しない。

AON原則にしよう。

## AONを一つの原則として含む哲学についての問い

AONは単体じゃないと思うんだよね。他にもにた考えとか近しい場所の哲学でまとめられる可能性があって、AONはその一つかも。　どういうまとまりだとおもう？

## 当初のAI案「目的と必要と充足」

**目的と責務に照らして必要なものを捉え、その必要を過不足なく満たすための、実現の選択と評価を扱う体系。**

AONを核として、何が必要か、手段をどう位置づけるか、費用・困難さ・実施順序を必要性とどう関係づけるか、何をもって必要が満たされたと判断するかを扱います。

この体系が担うのは、**目的と責務に対する必要性を、実現する側の都合で変質させず、その充足に即して判断すること**です。

前の「目的と実現」という広い定義を、この意味へ捉え直します。各領域に固有の対象や成立条件は、それを担う体系を参照しながら、必要性と充足の観点から判断します。

3．目的と必要と充足の哲学

目的と責務に照らして何が必要かを捉え、その必要を満たす実現の選択と評価を扱うこと。

「必要性」を題名では「必要」と表します。**目的に対する必要と、その必要が満たされること**という関係を名指すので、AONを核とする意味にも合います。

## 提案後の判断と、AONの位置づけについての訂正

これで一旦決定しようか。

第三哲学についてなんだが、"AONを核とする哲学" にはしたくない。あくまで、その哲学の中に AON が存在しているだけで、中心的概念と決まったわけではない。もちろん、将来的にそうなる可能性はあるが今現在で断定したくない

## 訂正を受けたAIの応答

**AONは第3哲学に内包される採用済みの原則であり、第3哲学そのものの本質や中心的概念は、まだ確定していない。**

この区別は重要です。第3哲学が何を引き受けるべきかを先に考え、その責務範囲から本質と境界を定めていくべきですね。その過程でAONがどのような位置を占めるのかも、自然に見えてくるはずです。

AONから逆算して第3哲学の境界を定めてしまうと、SCBでいう、全体の欲求から下位のまとまりへ向かう考え方とも逆になってしまいます。

AON自体の定義や採用判断は維持します。

**第3哲学を独立した一つの哲学として考えるところから始めましょう。** AONの体系化を目的にするのではなく、第3哲学の本質を探究した結果として、AONを適切に位置づけるという順序です。
