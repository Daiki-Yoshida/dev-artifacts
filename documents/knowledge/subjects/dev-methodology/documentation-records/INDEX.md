# 文書と記録の方法論〈仮称・草案〉

**開発中の判断と観察をその時点で残し、後の主体が、現在使える知識とその根拠をたどれるようにする。** 読み手には、明日同じ作業を再開する自分も含む。この草案は、経過の保存、現行文書の更新、次の主体への引継ぎを扱う。

ある開発者が「形式Aで失敗した」と書けば、その時点でそう報告したことが残る。どの条件で何が起きたかは、対象データや実行結果と照合する。原因についての解釈や当時の意図を補うときは、誰が何を根拠にそう読んだかを示す。あとから判明した事実を使う場合も、当時の表現を保存し、新しい理解と結び付ける。こうすれば、いまの説明を改善しても、以前の判断を当時の条件で検討できる。[RTC哲学](../../dev-philosophy/RTC.md)

## 経過を残す

判断を採用・変更したとき、予想に反する事実が分かったとき、検証を終えたとき、中断や担当交代のときに、その時点で残すべき経過を考える。長く区切りが来ない場合は、到達点と残る問いを短く書く。記録の詳しさは、次の主体が引き受ける判断と、失うと取り戻せない根拠に応じて選ぶ。

たとえば検証結果なら、確かめた対象の版・条件・観察結果を、再び特定できる範囲で残す。採用判断なら、誰がどの立場で、何を理由に、どの範囲まで採用したかを書く。人から聞いた結果には報告者、自分の解釈にはその根拠を添える。当時の発言や測定結果が判断を左右したなら、該当する原文や実行結果への参照を残す。元資料を確認できていない箇所は、その範囲が分かるように書く。[主体の判断と経過を記録する意図](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/records/2026-10-13-work-records-proposal/USER_MESSAGES.md)

## 現行文書を更新する

決定や検証によって読者の行動が変わるときは、その仕様や方針を所有する文書に、現在有効な内容と適用条件を反映する。採用の根拠は判断時の記録へ、判断時の記録からは必要に応じて現行の説明へ辿れるようにする。後で誤りが見つかったら、訂正の理由と根拠を残し、現行文書を更新する。当時の発言・報告は、当時のものとして読める形で保持する。

たとえば運用担当者が「平日の問い合わせには翌営業日までに一次回答する」と決めたとする。利用者向け案内には、対象と期限を記す。その案内を保守する人には、決定者と採用範囲を確認できる議事記録への参照が役立つ。後日対象が拡大したときは、新しい決定を記録して案内を改める。これで利用者は最新の約束を知り、担当者は過去の問い合わせに当時どの約束が適用されたかも調べられる。

## 引継ぎと保存を確かめる

引継ぎの入口には、到達点、次に判断すること、必要な条件と根拠を示す。却下案や訂正の経緯は履歴に保持し、読者の判断が変わる場合や同じ誤りを防ぐ場合に、その箇所を案内する。記録を移したときは、移管先で必要な内容が読めて、引継ぎの入口からそこへ届くことを確かめる。移管先への保存が確かめられるまで元の記録を保持する。[RTCのNALと適切な伝達](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/dev-philosophy/RTC.md)・[記録移管に関する採用判断](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/records/2026-10-13-work-records-implementation-adoption/RECORD.md)

Workへの適用では、Work側が「どの仕事の、どの判断と状態を引き継ぐか」「何が保存できれば終了へ進めるか」を定める。本方法論は、後の担当者が記録からその意味を読み取れ、現行知識と根拠を実際に参照できるところまでを扱う。記録の保存先や承認経路は採用先の規則に従う。
