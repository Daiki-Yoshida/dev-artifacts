# Work方法論（草案）

**Workとは、一つの目的について、誰が何を引き受け、どの結果を確かめれば達成と言えるかを定め、そこに属する作業・判断・成果を開始から終了まで扱う単位である。**

たとえば「来場者が使える入口に案内を直す」という依頼では、会場担当の回答、Webの修正原稿、印刷用PDFの校正紙が別々の場所にある。Webの担当者が「直しました」と答えても、来場者に渡るPDFの矢印は古いかもしれない。この三つを一つの目的に結び、残りを引き受ける人が作業を続けられ、依頼者が両方の結果を確かめられるようにするのがWorkの目的である。

## 一つにする仕事を決める

依頼を受けたら「誰が、何をできるようになれば、この依頼は済むか」を一文にする。二つの変更が揃って初めてその結果が出るなら、同じWorkに含める。上の例ではWebとPDFを別々の担当者が作っても一件である。途中で「会場内の全標識も多言語化したい」という要望が出たら、それだけで採否や達成を決められる。別の依頼として受け、引き受けた時点で元のWorkに参照を残す。元の依頼の成果そのものを変えるなら、その変更を決められる人と合意し、以前の範囲と変更理由を記録する。

対象はGit・GitHubとフォルダ管理を使えるプロジェクトである。原稿の編集にもソフトウェアの改修にも、以下の手順を使える。

関係者が共有するWorkの正本をGitHubに置く。相談に参加していなかった人や別のAIにも、Workの入口を一つ渡せばよい。そこから「何を頼まれたか」「今はどの判断が有効で、その理由は何か」「どの版を開いて何から始めるか」を辿れるようにする。チャットで重要な判断が決まったら、担当者が決定内容・理由・対象を作業文書に残す。すでにIssue上で決まった事柄なら、その発言を参照する。

## 一つのWorkを何で表すか

| 要素 | 役割と使い方 |
| --- | --- |
| **Work Identity（ワークアイデンティティ）** | どの目的を引き受けた仕事かを一貫して識別し、その仕事に文書・成果・資源を帰属させる。実務上は `<種別>/<目的を表す名前>` で呼ぶ。例は `fix/venue-entrance`（会場入口の訂正）。担当交代や検証のやり直しでも同じ名前を使う。 |
| **Work Issue** | そのWorkの依頼者と担当者が、目的・達成条件・進行状況と作業文書への入口を共有するGitHub Issue。この草案の標準例では、既存の依頼Issueをその役に使い、適当なものがない場合に作る。関連する別のIssueもここから辿れる。 |
| **Workドキュメント（Work Documents）** | そのWorkを実行する人が更新する作業文書。現在の計画、対象の資料、確認済みの範囲、次の手を置く。Gitで版を管理する。Work Issueから開ける入口を一つ決める。 |
| **Work Records** | Workドキュメントのうち、担当がその時点で何を見てどう判断したかを残す経過記録。次の担当には当時の根拠、終了後にはプロジェクトの履歴になる。 |
| **成果物の版と変更提案** | 実際に変えた原稿・コードなどは、それを管理するリポジトリに保存する。Workの作業文書から該当するPRやコミットを辿り、検証結果から確認済みの版を特定できるようにする。 |

依頼や範囲変更の合意がIssueのコメントで行われたら、そこが合意の原文になる。担当は作業文書の対象・残件を更新し、そのコメントを指す。校正や試験の結果はRecordsに書き、依頼者が次の判断をするときに、Issueから結論と記録を辿れるようにする。記録の作り方・訂正・保存確認が初めてなら、[文書と記録の方法論](../documentation-records/INDEX.md)で一件の記入から試せる。

## 最初の一件を開く

1. **共有先を見つける。** GitHubで、プロジェクト全体の案内や進行中の仕事を置くリポジトリを開く。これが作業文書の**管理用リポジトリ**である。一つしかない現場ではそのリポジトリを使う。関係者が日常の進捗を読むブランチを**基準ブランチ**と呼ぶ。初導入なら、プロジェクトの担当者と管理先・基準ブランチ・文書の反映方法を決める。単一リポジトリなら、デフォルトブランチをその候補にできる。
2. **既存Workか新規かを決める。** 依頼を表す言葉で管理先のIssuesと進行中の作業文書を探し、名前に加えて達成条件を照らす。一致すれば下の「引き継ぐ」へ進む。相談中で目的が定まらなければIssueに問いを置く。新たに成果を引き受ける時点で、依頼の範囲を決める人とIdentity・担当・達成条件を確かめる。
3. **依頼の窓口を用意する。** 既存の依頼Issueを使うか、管理用リポジトリに作る。タイトルには成果が分かる名前、本文には下の例にある情報を書く。依頼を引き受けた人は、このIssueから作業文書を開けるようにする。Issuesを使わない現場なら、次に作る文書を共有の窓口にも使い、プロジェクトの案内からリンクする。
4. **作業文書の最初の版を共有する。** 本書では管理用リポジトリの `.worktrees/<種別>/<名前>/documents/` を標準配置とする。この配下に、たとえば `STATUS.md` を作り、依頼への参照、最初の対象と次の一手を書く。現場の公開手順に従って基準ブランチへ反映する。Issueに実際に開ける文書のリンクを貼り、自分でもそのリンクを開く。基準ブランチへの反映待ちなら、現在読める版と反映待ちであることを示す。

最初の一件の**記入例**を示す。以下の番号と案件は架空。実際には手元のIssue番号・ファイルURLに置き換える。

| 書く場所 | 最初に書く内容 |
| --- | --- |
| Work Issue `#14` のタイトル・本文 | 「会場案内を北口に訂正する」。Workは `fix/venue-entrance`、担当は案内編集係。達成条件は「来場者向けのWebと配布PDFの両方で、入口名と矢印が会場担当の回答に一致する」。作業文書は次の行のファイルへリンクする。 |
| `.worktrees/fix/venue-entrance/documents/STATUS.md` | 「依頼は #14。会場担当の回答は #14 の確認コメント。対象はWeb原稿 `guide/entrance.md` と配布用PDF。両方とも照合前。最初に現在の原稿と校正紙を開き、入口名と矢印の位置を確認する」。別のリポジトリや共有フォルダにある対象には、関係者が開ける所在を添える。 |

`.worktrees/` はこの配置で仕事ごとの資料を収めるフォルダ名である。並行編集で作業場所を分ける必要があれば、作業用のブランチやworktreeを用意する。複数のリポジトリを変更する場合でも、仕事全体の作業文書は決めた管理先に置き、各リポジトリが所有する変更の版を指す。

## 進める・引き継ぐ

作業を始めた人は、Workドキュメントから対象を開いて一つ実行し、結果を達成条件と照合する。判断が変わった、検証が終わった、中断する、といった節目で `documents/records/`（上のWorkフォルダ内）に経過を残し、作業文書の次の一手を更新する。長引く場合も、判明事項がまだ手元にあるうちに短く書く。専用の校正コピーや検証環境を作ったら、その場所と返し方を作業文書に添える。共有の地図原本、Work専用の校正紙、一回の出力用一時ファイルは、使い終える時期も片付ける人も異なる。専用環境を使う場合は、作成・検証・停止の各操作で同じWorkの資源を指定できるかを照合する。[停止時だけ対象の指定が抜けた実例](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/records/2026-09-27-work-runtime-lifecycle-propagation/RECORD.md)

たとえば `records/web-proof.md` に「案内編集係が会場担当の回答とWeb原稿を照合し、北口の表記と矢印の一致を確認。PDF校正第2版は表記だけ確認。次は2ページの矢印を照合する」と書く。Web原稿には、照合したコミットのファイルへの固定リンクを貼る。外部の校正紙には共有先と版を添える。Issueから辿る**現在の作業文書**は新しい進捗に追従し、記録が指す**確認済みの版**は後から原稿が更新されても特定できる。

### 手元で進めるときと、誰かに渡すとき

手元では、原稿の編集と同じように、判断と次の作業を分かった時点で書き、戻りたい区切りでコミットする。まだ書き直しそうな校正案はローカルのコミットに留められる。確認が済み、関係者がその結果を使える段階なら、プロジェクトの手順に沿ってpushし、必要に応じてIssueの要点やリンクを更新する。記録を一行書くたびにGitHubへ反映する必要はない。

途中案でも、別の環境にいるAIに校正を頼むなら、その時点が共有の区切りになる。たとえば、作業ブランチに校正案をpushし、「北口の表記は確認済み。矢印は仮案。第2版の2ページを見てほしい」と対象版へのリンクを渡す。同じ作業場所を読める相手なら、手元のファイルと版を指定してもよい。いずれの場合も依頼先が必要な版を開けるかで判断する。普段の案内を読む人は引き続き基準ブランチを参照できる。

### 発見した問題と、その引受先を結ぶ

校正の結果、「PDF第2版の2ページで矢印が南を向いている」と分かったとする。これは依頼時の達成条件に関わるので、同じWorkで印刷担当が修正を引き受ける。現地の標識にも誤りを見つけたら、元のWorkに観察と場所を残し、標識の修正を引き受けた仕事にリンクする。連絡を済ませて返事を待っている間は「標識担当へ連絡済み、回答待ち」と書けば、後任にも実際にどこまで進んだかが伝わる。

担当が分かれる場合、作業文書には全体の達成を確かめる人と媒体ごとの引受先を書く。たとえば「Web担当は公開版を照合済み（確認した版へのリンク）。印刷担当が矢印を直し、第3版を提出。次は案内編集係が第3版の2ページを会場担当の回答と照合する」。現地に掲示された紙を確かめる場合は、後任が同じ現物を見つけられるように「北口改札横の掲示板、4月2日15時に確認、右下の版表示は第2版」のように場所・時点・見分け方を残す。

**途中から仕事を渡された人**は、Work Issueまたは作業文書を開き、Identity・達成条件・担当を確認する。この例で案内編集係を引き継いだ人は、最後のRecordで第2版の不具合を読み、作業文書が指す第3版を開く。手元の版と照合し、2ページの矢印が会場担当の回答どおり北を向くかを確かめる。リンク切れや未送信の資料があれば、特定できなかった資料と版を担当に返す。印刷を外部に委ねることになっても、「来場者に渡るPDFが正しい」という達成条件は続く。同じWorkに新しい引受先と納品版の確認方法を書き、実物を照合した結果を返す。

## 成果を確かめて閉じる

1. 依頼時の達成条件を読み返し、利用者が受け取る成果物を開いて一つずつ確かめる。会場案内なら実際に配布するWebとPDFの両方を開く。最終のWork Recordに結果・版・残件を記す。WebのPRが取り込まれてもPDFが未確認なら、Issueに残る作業と担当を返して続ける。
2. 今後の利用者が必要とする仕様や案内をプロジェクトの現行文書に反映する。Work Recordsは管理用リポジトリの `documents/archive/works/<種別>/<名前>/records/` に保存する。元記録を保持したまま内容を照合し、必要な公開手順を経て、共有先から開けることを確認する。移管先の同名ファイルの内容が違う、または一部が未公開なら双方を保持し、終了を保留する。
3. 保存を確認できたら、片付ける権限の範囲でWork専用の作業文書や資源を整理する。今後も使うものは引受先と用途を残す。Work Issueの作業リンクを終了後も読める成果・履歴のリンクに更新し、達成と終了の結果を報告する。そのIssueがこの仕事専用なら閉じる。他の仕事も追跡しているIssueなら該当部分の終了を記す。

たとえば「WebとPDFは北口を確認。履歴の公開待ちで終了保留」と「両媒体を確認し、履歴を共有先で照合。終了」は違う報告になる。中止のときは、中止を決めた人、理由、達成済みと未達の範囲、残る成果・資源の引受先を記録し、引渡しを確認して閉じる。

## この草案の根拠

旧版の共通開発指示（Artifact v2）を採用する現場では、具体的な実装前に既存の確定Workを再利用するか、新規Identityを依頼の決定権者（Owner）が明示確認する、またはその事前委譲の範囲で確定する、という規則がある。作業文書の管理元・標準配置と履歴の移管も旧版に根拠がある。[Identityの適用範囲](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S001_IDENTITY_MODEL.md)・[文書の配置と所有](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S003_WORK_DOCUMENTS.md)・[終了条件](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S004_LIFECYCLE_AND_RESOURCES.md)

Work Issueには、実際に `feat/rule-class-contract` をIssue #219から追った例がある。本稿で示した窓口の使い方は、その実例をもとに初導入の人向けに組み立てた案である。専用Issueの全件必須化や一対一対応は未決である。目的変更時の分割と中止時の手順も草案に属する。[Work Issueの実例](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/records/2026-10-31-rule-class-adoption/RECORD.md#implementation-reference)・[今回の読者と文書の要件](../../../records/2026-11-27-methodology-practice-contract/RECORD.md)

今回の改稿では、プロジェクト文書をGitで管理し、手元の保存とGitHubへの共有時期を選ぶという[Ownerの発言](../../../records/2026-11-27-work-context-sharing/RECORD.md)を反映した。共有を待てる場合と途中案を手渡す場合の校正例は、本稿での具体化である。実際に、人間・ブラウザ上のAI・CLI担当の間で何を引き継ぐか、手元の記録をいつ共有するかを扱った経緯は[Issue #204](https://github.com/Daiki-Yoshida/dev-artifacts/issues/204)から辿れる。
