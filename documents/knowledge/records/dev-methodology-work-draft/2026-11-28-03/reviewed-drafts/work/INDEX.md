# Work方法論（草案）

**一つの成果を引き受けたら、そのWorkに名前を付け、作業文書・変更した版・残件を結び、別の担当がGitHubから続きを始められるようにする。** 成果を確かめ、後に残す文書と記録を引き渡すところまでが一つのWorkである。

対象は、Gitで版を管理し、GitHubで関係者がその版を共有し、プロジェクトのフォルダに作業文書を置ける現場。たとえば、イベント運営で会場案内の原稿と配布用PDFを管理しているチームでも使える。Work名は引き受けた目的から決める。Gitはその作業の版を特定し、GitHubは担当者が同じ版・経過・公開状態を確かめる場所となる。記録をどう書き、訂正し、保存を確認するかは[文書と記録の方法論](../documentation-records/INDEX.md)を使う。

## 1. 成果を決め、Workを開く

1. プロジェクトの管理用リポジトリで、進行中のWork文書と関連するIssueを探す。すでに同じ成果を引き受けていれば、そのWorkの続きから始める。相談から実作業に移るとき、新しい目的には `<種別>/<成果を識別できる名前>` を付ける。Artifact v2を採用する現場での具体的な実装は、新規IdentityをOwnerが確認するか、その選定・確定を事前に委ねた範囲で始める。[既存の適用条件](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S001_IDENTITY_MODEL.md)
2. 最初の作業文書に、引き受ける担当、成果、達成を確かめる方法、対象ファイルや外部資料の所在を書く。共有の入口には管理用リポジトリの**基準ブランチ**を使う。これはプロジェクトが進行状況を共有するブランチで、名前と公開手順は各現場が決める。
3. 成果物を変更するリポジトリでは、その現場の手順に従って作業場所を選ぶ。並行編集を分けるためにブランチやworktreeを作ったら、作業文書から辿れるようにする。IssueやPRを使う場合はそこでの依頼・レビューへリンクする。担当やPRが増えても、作業文書の管理先は一か所に保つ。

**記入例（架空）**　Work名は `fix/venue-entrance`。担当は案内編集係。依頼は「来場者が現在使える入口に着けるよう、案内を直す」。会場担当が確認した入口名を根拠に、配布するWeb案内とPDFの両方で入口名と地図の矢印が一致すれば達成。Web原稿とPDF版下を別々のリポジトリで編集しても、一方だけではこの依頼を満たせないので一つのWorkとして扱う。進捗の入口には、たとえば管理用リポジトリに作った `.worktrees/fix/venue-entrance/documents/STATUS.md` を使う。

## 2. 変更と判断を同じ仕事から辿れるようにする

次は管理用リポジトリを起点とするArtifact v2の標準配置。単一リポジトリならそのリポジトリが管理を兼ねる。作業文書は管理元のGitが追跡する。フォルダ名の `.worktrees` は、この文書を置くためにGit worktreeを新設するという意味を持たない。[作業文書の配置と管理元](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S003_WORK_DOCUMENTS.md)

| 何をしたとき | どこに何を残すか |
| --- | --- |
| 作業を始めた、計画や担当が変わった | `.worktrees/<種別>/<名前>/documents/` の作業文書を更新する。これを読めば今の対象・担当・残件が分かるようにする。 |
| 重要な判断をした、予想と違う結果が出た、検証を終えた | 同じ場所の `records/` に、担当がその時点で何を確かめ、なぜそう判断したかを書く。関連する変更はリポジトリとコミット、外部の校正紙などは読める保存先と版で指す。ひと区切りを一つの短い記録にまとめてよい。 |
| 長引いた、中断する、担当が替わる | 記憶や手元の未保存ファイルにしかない進捗を記録する。対象の版、残件、次の具体的な操作を一緒に渡す。 |
| 専用の環境・資料を用意した | 作成時に、誰がどこで使い、どう特定して返すかを書く。たとえばイベント共通の地図原本、当該Workの校正用コピー、一度の出力で使う一時ファイルを区別する。専用環境なら起動・検証・停止が同じ対象を指すことを確かめる。[旧運用で停止対象のずれを発見した記録](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/records/2026-09-27-work-runtime-lifecycle-propagation/RECORD.md) |

手段の変更は同じWorkに理由を追記する。**目的を変更・分割する場合の草案**として、引き受けた成果を変えるときは決定できる人と再合意する。たとえば「会場内の全標識を多言語化する」という提案は、入口案内の訂正とは別々に採否と達成を判断できる。別Workで引き受ける場合は、元のWorkに残す範囲と双方の参照を記す。

## 3. GitHubから引き継いで再開する

前任は管理用リポジトリで作業文書と判断の記録を、成果物のリポジトリで変更したファイルをそれぞれGitの追跡対象に含め、現場の権限・手順で必要な版をGitHubへ反映する。**現在の作業文書を探す入口**と、**実際に確認した時点のファイル**を渡す。前者には基準ブランチ上の場所、後者にはGitHubで対象ファイルをそのコミットに固定したリンクが使える。記録や成果が別リポジトリ、またはGit外の原本にあれば、それぞれの版と参照先を渡す。

> **会場案内の引継ぎ記入例**　会場担当の回答は「北口」。Web版は回答と照合済み。配布用PDFは表記を直したが、地図の矢印は未確認。作業文書に会場担当の回答、確認したWeb原稿、PDF校正第2版の保存先を添付した。次の担当は第2版の2ページを開き、矢印を確認して配布版を出力する。

後任は共有の入口から記録を開き、確認済みの版を特定し、現在の版と照合して最初の未確認項目に着手する。たとえばGitHubでWeb原稿の固定リンクを開き、手元にも同じコミットがあれば `git show <コミットSHA>:guide/entrance.md` で当時の表記を読める。手元だけで保存した、コミットした、GitHubの作業ブランチへ送った、基準ブランチに反映された、の各状態を報告で区別する。たとえば作業ブランチにだけある場合は、そのリンクと基準ブランチへの反映待ちを伝える。未送信の校正紙があるなら、その所在と受け渡しの残件を添える。

## 4. 成果を判定し、記録と資源を引き渡す

1. 参加した各リポジトリで、対象の変更がどこまで反映されたかと残件を確認する。最初に約束した条件を、利用者が実際に使う版で確かめる。会場案内なら配布先のWebとPDFを双方開き、確認した版と結果をWork Recordsに書く。片方のPRだけが統合された時点では、残る媒体と担当を明記して続ける。
2. 今後の担当者が使う案内や手順は、その主題を管理する既存の文書に反映する。作業中にだけ必要だった校正メモを選別し、経過を記した **Work Records** を管理用リポジトリの `documents/archive/works/<種別>/<名前>/records/` に移す。
3. 必要な保存・公開手順を経て、元の記録を残した状態で、移管先に各記録の内容が揃い、関係者の入口から根拠を開けることを確認する。既存の同名資料と衝突したとき、一部しか保存されていないとき、必要な公開が保留のときは元記録と既存資料を保持する。保存済みの範囲を照合してから再開する。
4. 移管の確認後、Work専用の校正コピーなどを権限の範囲で整理する。引き続き使う資源は所有者と保持理由を残す。別の催しでも使う地図原本はプロジェクトの管理に残る。最終報告には**成果の達成状況**と**Workの終了状況**を記す。たとえば「両媒体で北口を確認。校正記録の移管が未確認のため、元記録を保持して終了を保留」。[既存の終了・移管条件](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/work-identity/S004_LIFECYCLE_AND_RESOURCES.md)

**中止時の草案**では、中止を決めた人、理由、達成した範囲、未達の扱い、残す成果・資源の引受先を最終記録に書く。記録の保存と引き渡しを確認できたら「目的は未達、中止により終了」と報告できる。
