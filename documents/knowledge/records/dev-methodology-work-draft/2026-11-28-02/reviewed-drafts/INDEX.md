# 開発方法論

**Stage 2-Bの草案。** 公開済みの[SERA開発哲学の仮決定版](https://github.com/Daiki-Yoshida/dev-artifacts/blob/7c9468ed4c8270c156b930d94ea6335a14856985/documents/knowledge/subjects/dev-philosophy/INDEX.md)を基礎に、人が単独でも使える開発方法を検討する。今回は一つの開発目的を引き継ぎ、最後まで扱えるかを検討の出発点とした。[草案化の依頼と判断範囲](../../records/2026-11-26-work-methodology-draft-request/RECORD.md)

| 知りたいこと | 草案 |
| --- | --- |
| 何を同じ仕事として扱い、文書・Git・環境・担当をまたいで継続し、どこで終了するか | [Work方法論](work/INDEX.md) |
| 過去に何が起きたかを保存し、現在の説明を更新し、後の人が両方を確かめるにはどうするか | [文書と記録の方法論〈仮称〉](documentation-records/INDEX.md) |

Work方法論は、引継ぎの際に後任が何を判断できればよいか、記録の保存結果がWorkの終了にどう影響するかを定める。記録の作成・訂正・継承の方法は、文書と記録の方法論を参照する。後者はプロジェクト全体に関する決定のように、個別のWorkを特定しない場面にも使える。

旧Artifact v2で採用済みの運用は、各草案の出典から辿れる。ここで新しく提案した判断基準や例は、再編ブランチでの検討材料として扱う。
